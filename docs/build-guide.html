RescueRelay build guide

How the recovery coordinator is built, why its boundaries matter, and how to run the complete local workflow on your own computer.

Author: Krishna Kallamadi · Connect on LinkedIn · GitHub

Scope matters. This is a local-first reference implementation, not a production dispatch service. Seeded names, locations, rescue events, travel estimates, and outcome metrics are synthetic. Notifications remain inside the application. No real volunteer is contacted, no live route is booked, and no food-safety certification is provided.

Step 01

Define the product boundary

RescueRelay focuses on a narrow operational question: when an assigned driver can no longer collect a donation, which eligible alternative can finish the pickup and delivery within the known constraints, and what should a coordinator approve?

Decision. Start with sealed shelf-stable donations, explicit time windows, known volunteer capacity, recipient acceptance rules, explainable replacement proposals, and a human approval gate. Keep unsupported food handling outside automated assignment.

In this implementation

Organization-scoped accounts, donors and recipients, volunteers, donation and rescue records, cancellation and recovery, recipient confirmation, audit history, CSV utilities, responsive web screens, and an Expo mobile client.

Not represented as implemented

Live traffic or navigation, SMS or push delivery, cold-chain validation, predictive dispatch, payments, enterprise identity federation, signed store binaries, operational SLAs, or partner-system integrations.

The product opportunity is a hypothesis to validate with operators. Replacement notifications and routing already exist in established food-rescue platforms; RescueRelay does not claim to be the first such system.

Step 04

Model the operation before building screens

  1. Identity and scope. A user belongs to one organization and has a coordinator, volunteer, or recipient role. Registration creates a new isolated organization. Only its coordinator creates additional role-bound accounts.
  2. Partners and resources. A donor provides the pickup location. A recipient specifies acceptable categories, capacity, and opening hours. A volunteer has availability, capacity, location, and training status.
  3. Donation and rescue. A donation records weight, servings, packaging, and pickup window. A rescue connects that donation to a recipient, a delivery window, and an optional driver.
  4. Forward progress. An assigned rescue must be accepted before it can be marked picked up, then delivered. Receipt confirmation is a separate acknowledgment. Cancellation before pickup opens recovery; a custody interruption after pickup retains the holder and must escalate rather than silently allocate a new driver. Only a coordinator can record the final disposition. Recovery cannot resume while food remains in custody.
  5. Evidence. Policy citations, constraint checks, candidate rejection reasons, tool traces, audit events, and in-app notification records explain what happened.

Decision. Treat serving counts and weights as operational input fields, not verified impact measurements. Demonstration metrics summarize synthetic records and cannot substantiate claims about actual meals saved.

Implementation map: apps/api/src/state.ts defines seed data and configured policies; schemas.ts validates request shapes; app.ts enforces state transitions; packages/shared/src/index.ts is the client-facing type contract.

Safety boundary: the public type system names several food categories, but the current creation/import workflow accepts only sealed shelf-stable donations. A type name is not evidence of support for chilled, frozen, or prepared food.

Step 05

Build an explainable bounded recovery planner

The default planner works without an API key or internet model call. Its tools inspect an incident, retrieve relevant policy excerpts, find volunteers, estimate routes, check constraints, rank feasible candidates, and either propose replacements or escalate.

Inspect→Retrieve policy→Estimate→Check→Rank or escalate

Decision. Keep deterministic hard constraints authoritative. Travel feasibility, vehicle capacity, volunteer availability, recipient acceptance and opening hours, and supported handling must not become optional because an explanation sounds persuasive. The planner excludes volunteers with an active rescue or held food custody and reserves at most one new active rescue per volunteer, includes ten minutes of service at each stop, and requires a five-minute buffer before closing windows.

The planner builds a graph of feasible rescue–volunteer pairs and uses maximum bipartite matching under its one-active-rescue-per-volunteer rule. Augmenting paths can revise an earlier choice when another rescue needs a scarce driver. Candidate order favors local scores; the algorithm does not claim to minimize total travel. A multi-incident proposal is applicable only if every selected incident has feasible coverage. Partial feasibility does not authorize a partial apply.

Travel times are explicitly labeled synthetic-matrix values or distance estimates. They are not traffic-aware ETAs. The plan records citations with source/version, a tool trace, rejection details, a ten-minute expiry, and the version of state on which it depends.

Implementation map: apps/api/src/planner.ts owns retrieval, travel estimates, candidate checks, and maximum matching. provider.ts owns the optional read-only tool loop. Local policy passages come from state.ts; this is lexical retrieval, not a vector database or a hidden external knowledge service.

Agent versus workflow

The implementation is a bounded, state-driven tool orchestrator: the incident and feasibility findings determine which reasoning steps and escalation path are relevant. In offline mode it is not an LLM-driven agent or a general autonomous operator. The surrounding workflow is conventional application logic: authenticate, load state, check permissions, generate a proposal, request approval, commit a valid mutation, and record evidence.

A selected Fireworks, Nebius or OpenAI API provider can perform a bounded read-only investigation through the optional AI workspace only after local transfer review and explicit one-use consent. It selects from inspect_incident, retrieve_policy, find_volunteers, check_candidates, and ask_clarification. The server validates tool names, arguments, incident scope, and evidence coverage, with a limit of six turns and ten tool calls. It then recomputes deterministic eligibility. The provider cannot dispatch or override constraints; missing evidence can hold the proposal for clarification. Offline mode remains sufficient for the complete demonstration.

Step 06

Make approval a server-side guarantee

Every domain mutation includes the latest expectedVersion. Generating a proposal itself persists new state. Applying it therefore uses the returned snapshot version, not the version that preceded generation.

  1. Authenticate the coordinator and scope the request to the organization.
  2. Verify the submitted version, proposal status, proposal expiry, and current constraints.
  3. Apply only the reviewed proposal in a transaction and record the audit/notification changes.
  4. Use an idempotency key to make an identical approval retry safe. A key reused with different content is a conflict.
  5. Return a fresh snapshot. If the state is stale, stop and ask the operator to review newly generated evidence.

Never auto-approve after a conflict. HTTP 409 STALE_VERSION is a request to reload and review. Replaying with a new version without a new human decision defeats the safeguard.

The version covers the entire organization. Even an unrelated accepted mutation can make a proposal stale. That conservative choice is simple to audit, but finer-grained concurrency is a future design improvement, not a reason to bypass the review gate.

Implementation map: apps/api/src/store.ts owns SQL transactions, hashed sessions, and replay records; app.ts enforces authorization and approval; snapshot.ts filters data by role.

Browser tokens belong in memory, not persistent browser storage. The native client uses secure OS storage when available, with an explicit memory-only fallback; the Expo web target also keeps its token in memory. Logout revokes the current session. Role-filtered snapshots reduce exposure: volunteers see their assigned work; recipients see their own rescues; neither receives coordinator plans or organization-wide audit history.

Windows launchers

After npm ci, double-click start.bat, stop.bat or restart.bat in the checkout (or use .\start.bat from PowerShell). The files resolve their own folder, including spaces and different drives; the npm wrapper uses pushd/popd for UNC paths. See the full launcher instructions.

Start opens a visible console and waits for the API and web app at http://127.0.0.1:5173. Repeated start reuses the recorded session; repeated stop is safe. Stop/restart validate the supervisor's checkout, token, PID and creation time, then stop only its Windows job. Unrelated processes and manual sessions are never killed. Stop an earlier manual session with Ctrl+C; occupied ports 4000/5173 cause a clear refusal.

The launchers require Windows 10/11, PowerShell 5.1+, Node 24.x and npm 11+. They keep the demo on loopback with external AI calls off. Logs/state are local in ignored .rescuerelay/. Keep the console open, or use Ctrl+C to stop it. No execution-policy changes or automatic dependency installation are performed.

The landing page's 12-second SVG/CSS animation shows sealed pantry goods moving from donor to volunteer to recipient. A visible Pause/Play control and a static reduced-motion presentation keep the story accessible. It is illustrative, not live tracking.

Internal web pages use a professional local system sans-serif font, 16px body and control text, 14px supporting text, and a consistent heading hierarchy. Responsive cards, forms and AI panels wrap to preserve readable text instead of shrinking it. No external font service is required.

Open http://localhost:5173 for the web UI. The API defaults to http://127.0.0.1:4000/api. The Vite development proxy connects the browser to the API. On Windows PowerShell, replace the copy command with Copy-Item .env.example .env.

Step 08

Exercise one recovery from start to finish

Use only the synthetic demonstration workspace for this walkthrough. The baseline already contains rescue r-101 awaiting recovery; start there to practice proposal review. To exercise a new cancellation first, use the still-assigned r-102. Reset the baseline when you need fresh time windows.

  1. Enter as coordinator. Inspect the rescue board, donor, receiving location, pickup deadline, and current driver. Notice the demonstration and notification labels.
  2. Record a cancellation. Choose an assigned rescue and enter a reason. The server removes it from normal execution and creates a recovery need.
  3. Generate a proposal. Open recovery planning. Read the candidate checks, rejection reasons, policy excerpts, route-estimate label, trace, and expiry. If no candidate is feasible, review the escalation rather than forcing an assignment.
  4. Approve deliberately. Apply the ready proposal once. Check that the rescue has the replacement driver awaiting acceptance, that a notification appears in the in-app outbox, and that an audit event records the action. Approval is not evidence that the volunteer has agreed or been contacted.
  5. Complete the route. Use the appropriate assigned volunteer role, or coordinator controls, to record acceptance, then mark pickup and delivery. A recipient account can acknowledge only its own delivered rescue.
  6. Inspect the record. Review the final status and audit. Export only synthetic data during demonstration. Do not describe the displayed result as a real rescue outcome.

Synthetic worked example

Harbor Market has 64 kg of sealed pantry goods for Maple Community Kitchen. Alex is unavailable; Maya already has an active rescue; Sam can carry only 20 kg. The baseline gives Jordan 90 kg of capacity and an illustrative 8-minute trip to the donor plus 14 minutes to the recipient. Priya is another candidate, but the estimated journey is longer. With fresh baseline windows, the planner can recommend Jordan only after every eligibility check passes. Try the refusal paths

The demo reset API supports baseline, no_capacity, and tight_window scenarios. The latter two intentionally make recovery infeasible. Also open two coordinator sessions: after one changes state, an older approval must fail with a conflict rather than silently overwrite the newer decision.

To resolve an escalation, a coordinator uses POST /api/rescues/:id/resolve with a reason and resolution of resume_recovery, delivered, or cancelled. The server blocks recovery resumption when custody is still held. Recorded completion remains a human report, not independent physical verification.

The former /api/plans/:id/explain route returns 410 USE_INVESTIGATION. The standard server rejects the legacy external mode: "provider" generation path with CONSENT_REQUIRED; prepare POST /api/ai/consents and explicitly execute POST /api/ai/operations instead. Existing proposal approval remains a separate action.

CSV donation import headers are donorId,description,weightKg,servings,pickupStart,pickupEnd. Import creates sealed shelf-stable records by design: verify the contents satisfy that restriction before using the import format.

Conflict handling: preserve error code and details for the operator, fetch a new snapshot, and request review. Do not “fix” a rejected approval by replacing the version and retrying automatically.

Step 12

Operate locally and troubleshoot safely

Eligibility, donor location, and receiving constraints cannot be edited while an active rescue depends on them. Resolve the existing commitment first rather than silently invalidating it. Post-pickup disruptions preserve food custody until a coordinator records the disposition.

Keep secrets and mutable data out of Git. Inspect the configured database path before backups or resets. The local utilities validate SQLite integrity, foreign keys, and the supported schema. Backup uses VACUUM INTO for a consistent snapshot, including committed WAL data. Restore creates a new file and invalidates sessions; it never overwrites an existing destination. Backups contain personal data and password hashes and require the same access protection as the live database. The application does not encrypt SQLite or backup files; configure filesystem permissions and storage encryption separately. Audit history is protected by application routes, not cryptographically tamper-proof against a filesystem administrator.

npm run db:backup -- --source data/rescuerelay.db --output backups/snapshot.db
npm run db:check -- --source backups/snapshot.db
npm run db:restore -- --source backups/snapshot.db --output data/restored.db

After a restore, stop the API, set DATABASE_PATH to the new file, restart, and sign in again. Test the restored workflow before relying on it. Only schema version 1 is supported; automated future schema migration is not implemented. A managed backup schedule, retention policy, and recovery objectives remain deployment work.

The API cannot start or SQLite is unavailable

Check node --version is 24.x, reinstall using npm ci, verify the database directory is writable, and read the server error. Do not delete a database merely to silence an error. Ensure another API process is not occupying port 4000.

The browser cannot reach the API

Start the API and web service, check /api/health, inspect the Vite proxy target, and confirm the port and allowed origin. A static web export alone does not include a running database/API server.

The phone reports a network error

Replace localhost with the computer's reachable address, verify both devices are on the same trusted network, check the API bind address and firewall, and restart Expo after editing its environment file. Do not expose the demo to a public network as a shortcut.

Approval reports stale state or the plan expired

Refresh the snapshot and generate a new proposal. Re-read the candidate checks and approve only after reviewing the updated result. This is intended concurrency protection, not a reason to disable the version guard.

No feasible volunteer is found

Read each failed constraint. Check training, availability, capacity, supported handling, pickup/delivery windows, and recipient acceptance. Use a fresh baseline reset for demo timing. Do not weaken a rule solely to make the demonstration succeed.

A notification exists but nobody received a text

That is expected. Notification records are in-app only. There is no SMS, email, or native push delivery adapter in the reference implementation.

Web reload asks for login again

The web client keeps the bearer token in memory rather than localStorage. A reload can end that client session experience; sign in again. Native storage differs and must be tested on real devices.

Before any real operational pilot

Disable demo access, configure TLS and restricted origins, provision identities through an approved process, review permissions and dependency alerts, define retention and deletion, validate food-handling procedures with responsible operators, configure backups and monitoring, and establish an incident/support owner. No checkbox here certifies legal or food-safety compliance.

Optional AI extension

Track every service decision explicitly

The complete 17-service decision matrix separates runtime adapters from alternatives, optional development tools and deferred human or account-connected workflows. All ten selected runtime adapters have source and passed mocked verification in the final local aggregate. A service being named, configured or implemented is not evidence of live access, enabled spending, verified credits or successful external operation.

All external adapters default OFF. Server-side enable flags and settings do not replace per-operation consent. Investigation consent binds a concrete sanitized evidence envelope, state version and hash; future bounded model/tool outputs are dynamic and cannot be previewed as one fixed wire body. No keys belong in the client, chat, screenshots or repository.

Build the consent boundary before connecting a service

  1. Keep the default safe. Clone, install and run without vendor credentials. Opening web AI Studio or native AI Assist reads local capabilities only. The browser reports configured, enabled, execution available and live-tested as different states.
  2. Review configuration locally. The server requires AI_EXTERNAL_CALLS_ENABLED, the provider's _ENABLED flag and its required settings. Values never appear in capabilities and no credential entry exists in either client. The table below lists names, not secrets.
  3. Prepare without sending. A coordinator chooses an operation and creates a local consent manifest. It binds the actor, organization, request, current version and a five-minute expiry. Investigation also binds the actual sanitized local evidence envelope and its hash; the selected model may later choose subsets and derive tool results. Separately disclosed external retrieval content may also be forwarded to that selected model.
  4. Inspect the disclosed transfer. Review recipients, model or parse tier, data categories, context or file hash, maximum request budget and retention warning. File previews show metadata and SHA-256; the whole selected file is transferred if confirmed. The full future model transcript is not knowable in advance.
  5. Execute once deliberately. Explicit confirmation consumes the consent before work. Missing settings, stale state, expired or reused consent fail closed. A local-only policy lookup is clearly labeled and sends zero external requests. Clients never automatically replay a failed operation or switch vendors.
  6. Review results separately. A generated plan still needs existing recovery approval. A reference draft can enter only the nonauthoritative reference collection. A voice draft creates a donation only after a human supplies and validates its structured fields; it never assigns a driver.
  7. Recover without guessing. Inspect local operation receipts after errors. Known file, job or memory identifiers and uncertainty guidance support manual reconciliation. A timeout is not proof that nothing reached a vendor; the app does not automatically delete uploaded copies or replay ambiguous writes.

Keep request and content limits explicit

Documents and audio are limited to 2 MiB decoded and checked for canonical base64 and basic matching signatures, not certified safe contents. The server bounds response bytes, request counts and per-request timeouts. Selected read-like calls may retry one HTTP 429 within the disclosed budget; write and ambiguous network failures are not automatically replayed. A byte limit does not verify document pages, recording duration or monetary cost.

Pinecone indexing accepts one to five human-approved references, divides them into deterministic chunks with bounded count and payload size, and submits one explicitly consented write. It does not index the configured hard-constraint collection, create a paid index or promise immediate search visibility. An accepted asynchronous write may create its organization namespace; an explicitly repeated upsert may incur embedding costs again. Do not mistake a submitted index write for a live retrieval benchmark.

Uploads, microphone capture, source discovery, preference management and reference publication are not native features in this build.

Web workspace refinement

Build the Rescue Pipeline and Organic motion

The selected workspace direction replaces the broad permanent sidebar with a full-width operational pipeline in cream and forest tones. Coordinator navigation is Today / Dispatch / Network / Impact / Workspace. Secondary pages retain food offers, community records, policies, activity/outbox, AI Studio and settings. Volunteer and recipient navigation remains role-specific; the API's accessible snapshot is the data boundary.

  1. Map existing states without inventing a workflow. apps/web/src/pipeline.ts derives exactly one lane for each rescue. The five active lanes are Recovery first, Awaiting approval, Awaiting acceptance, Assigned and In transit. Completed and Cancelled have explicit views, alongside All rescues. Escalated records remain in Recovery first; a custody warning remains visible.
  2. Keep approvals honest. Awaiting approval requires a ready proposal at the snapshot's version, unexpired at its recorded server time, with the rescue listed as an incident and in a replacement. This only identifies a reviewable proposal in the saved snapshot. Server-side approval still rechecks wall-clock expiry, version and constraints. Stale, applied and infeasible proposals do not imply approval readiness.
  3. Keep every action in the validated flow. PipelineBoard.tsx reads real snapshot records, derives counts and links to the existing rescue and plan dialogs. Actual assignment without acceptedAt is Awaiting acceptance. Delivered does not imply a confirmed recipient receipt. No drag-and-drop action changes custody, assignment or state. Offline and stale-data notices remain intact.
  4. Preserve readable, responsive presentation. pipeline.css scopes the full-width navigation, lane grid, cards and cream/forest palette to the workspace. Desktop lanes wrap into fewer columns on narrower screens; labels and controls remain readable. This is the responsive web/PWA surface, not a replacement for Expo's native screens.
  5. Add the chosen Liquid/Organic entry motion. Framer Motion drives the active indicator's scaleY expansion and staggered card/summary rise with spring bounce: 0.4. An attention banner slides down and settles with a brief small shake only when attention exists. Entry animation is designed not to restart on routine refreshes. The header's locally saved Reduce motion control and system reduced-motion preference provide a stable alternative. The existing landing-page Pause/Play animation remains independent.
  6. Verify behavior, not just screenshots. Focused mapping tests cover lane completeness and stale/expired/infeasible approval exclusions. Run npm run verify, inspect desktop and phone-width layouts through the real single-server API/client preview, exercise role switching and validated detail actions, and test quick navigation plus reduced motion. This revision's executed results and remaining limits belong in verification.md; source implementation alone is not browser certification.

Example: Harbor Market's synthetic pre-pickup cancellation appears in Recovery first. A current feasible proposal moves its display to Awaiting approval, where a coordinator reviews it. Approval creates an assignment; the replacement must accept before pickup. Pickup moves the record to In transit, delivery to Completed, and recipient confirmation remains a separate recorded step. A post-pickup escalation retains its custody warning rather than silently returning the food to an unassigned pool.

The display uses stored records and estimated servings, not live vehicle tracking or fabricated timing. Windows launchers, provider defaults, role permissions and server mutation validation are not relaxed by this redesign.
